# 编码规范与标准

## TypeScript/JavaScript 规范

### 类型安全
- 使用严格的 TypeScript 类型检查
- 避免使用 `any` 类型，优先使用 `unknown` 或具体类型
- 所有函数必须有明确的返回类型声明
- 所有函数参数必须有类型注解

### 代码注释 ⚠️ 强制要求

> **硬性规则**：所有代码必须有注释，无例外！

#### 函数注释（必须）
- **所有函数都必须添加 JSDoc 注释**，包含：
  - 功能描述（做什么）
  - 参数说明（@param）
  - 返回值类型及用途（@returns）
  - 异常情况说明（@throws，如适用）
- **即使是简单函数也必须注释**

#### 行内注释（必须）
- **复杂逻辑必须添加行内注释**，解释为什么这样做
- **关键步骤必须注释**
- **算法和业务逻辑必须注释**
- **魔法数字必须注释说明含义**

#### 文件注释（必须）
- **每个文件开头必须添加文件说明注释**
- 说明文件的用途和主要功能

示例（TypeScript）：
```typescript
/**
 * 用户管理服务
 * 提供用户信息的增删改查功能
 */

/**
 * 获取用户信息
 * @param userId - 用户ID
 * @returns 用户信息对象，如果用户不存在则返回 null
 * @throws {Error} 当数据库连接失败时抛出错误
 */
export async function getUserInfo(userId: string): Promise<User | null> {
  // 验证用户ID格式
  if (!isValidUserId(userId)) {
    return null;
  }
  
  // 从数据库查询用户信息
  const user = await db.users.findById(userId);
  return user;
}
```

示例（Python）：
```python
"""
用户管理服务
提供用户信息的增删改查功能
"""

async def get_user_info(user_id: str) -> User | None:
    """
    获取用户信息
    
    Args:
        user_id: 用户ID
        
    Returns:
        用户信息对象，如果用户不存在则返回 None
        
    Raises:
        DatabaseError: 当数据库连接失败时抛出
    """
    # 验证用户ID格式
    if not is_valid_user_id(user_id):
        return None
    
    # 从数据库查询用户信息
    user = await db.users.find_by_id(user_id)
    return user
```

#### 注释质量要求
- 注释必须清晰、准确、有意义
- 避免无用注释（如 `// 定义变量 x`）
- 注释必须与代码同步更新
- 使用中文注释（项目团队语言）

## Vue 3 / UniApp 规范

### 组件开发
- 使用 Composition API（`<script setup>`）
- 组件文件使用 PascalCase 命名（如 `UserProfile.vue`）
- 自定义组合函数必须以 `use` 开头（如 `useAuth`）
- 组件必须导出类型定义

### 状态管理
- 使用 Pinia 进行状态管理
- Store 文件放在 `store/` 目录
- 避免不必要的状态提升

### 性能优化
- 使用 `computed` 优化计算属性
- 使用 `watch` 和 `watchEffect` 监听变化
- 避免在模板中进行复杂计算

## Python / FastAPI 规范

### 代码风格
- 遵循 PEP 8 规范
- 使用类型注解
- 使用 async/await 处理异步操作

### API 设计
- 使用 RESTful 风格
- 使用 Pydantic 进行数据验证
- 使用 SQLModel 进行 ORM 操作

### 文档字符串
- 所有函数必须有 docstring
- 使用 Google 风格的 docstring 格式

## 代码风格

### 格式化
- 使用 2 空格缩进（前端）
- 使用 4 空格缩进（Python）
- 使用单引号而非双引号（字符串，前端）
- 每个文件末尾保留一个空行

### 命名约定
- 变量和函数：camelCase（前端）/ snake_case（Python）
- 类和组件：PascalCase
- 常量：UPPER_SNAKE_CASE
- 私有属性：以下划线开头

### 文件组织
- 一个文件一个主要导出
- 相关功能放在同一目录
- 使用 index.ts 作为目录入口（前端）
- 测试文件使用 `.test.ts` 或 `test_*.py` 后缀

## 项目特定规范

### 环境变量
- API KEY 和敏感信息必须放到 `.env` 文件中
- 不要将 `.env` 文件提交到 git
- 使用 `.env.template` 作为环境变量模板

### 导航（UniApp）
- 使用 `uni.navigateTo` 进行页面跳转
- 避免直接操作路由栈
- 页面路径统一管理

### 认证
- 使用 JWT Token 进行认证
- 前端使用 Pinia store 管理用户状态
- 统一处理认证失败的情况

## 测试要求

### 测试策略
- **实现优先**：先实现功能，确保功能正常工作，然后编写测试
- **测试跟进**：功能实现后立即编写测试，不要拖延
- **TDD 可选**：对于复杂算法、核心业务逻辑、或容易出错的部分，可以采用 TDD

### 单元测试
- 核心业务逻辑必须有单元测试
- 测试覆盖率目标：核心模块 > 70%（不强求 100%）

### 测试原则
- **边界覆盖**：覆盖正常流程、边界条件、异常情况
- **独立性**：每个测试用例应该独立运行，不依赖其他测试
- **可读性**：测试代码应该清晰表达测试意图，使用描述性的测试名称
- **快速反馈**：测试应该快速运行，避免过度依赖外部服务

## 代码质量

### 复用原则
- 严格遵循项目现有代码规范
- 保持与现有代码风格一致
- 使用项目现有的工具和库
- 复用项目现有组件
- 代码尽量精简易读

### 删除优化规则 ⚠️ 强制要求

> **硬性规则**：删除或优化代码时，必须进行全面的关联性扫描和深度测试！

#### 删除前必须执行的检查（强制）

1. **全局关联性扫描**
   - 使用 grep 搜索整个代码库中的所有引用
   - 检查函数/类型/变量的直接调用
   - 检查间接依赖（如通过导出的模块）
   - 检查配置文件中的引用
   - 检查测试文件中的引用

2. **影响范围分析**
   - 列出所有受影响的文件
   - 分析每个调用点的上下文
   - 评估删除后的功能影响
   - 确认是否影响用户可见功能

#### 删除后必须执行的验证（强制）

1. **编译检查**
   - 前端：确保无编译错误
   - 后端：确保 Python 语法正确

2. **功能测试**
   - 运行相关的单元测试
   - 如果涉及页面功能，必须进行本地 H5 测试
   - 验证相关功能正常工作

#### 违规后果
- 未进行关联性扫描的删除视为不完整
- 删除后未验证的代码变更不允许提交
- 导致功能回归的删除必须立即回滚

### 错误处理
- 使用 try-catch/try-except 处理异常
- 提供有意义的错误信息
- 记录错误日志
- 优雅降级，避免应用崩溃

### 性能考虑
- 避免不必要的计算和渲染
- 使用懒加载优化首屏加载
- 图片和资源优化
- 避免内存泄漏

## 文档要求 ⚠️ 强制要求

> **硬性规则**：代码变更必须实时同步更新文档，无例外！

### 文档同步规则（强制）
- **代码变更时必须立即更新相关文档**
- **不允许先改代码后补文档**
- **文档与代码必须保持 100% 同步**
- **每次提交前必须确认文档已更新**

### 必须更新的文档类型
1. **代码注释**：逻辑变更时立即更新
2. **API 文档**：接口变更时立即更新
3. **README**：功能变更时立即更新
4. **设计文档**：架构变更时立即更新
5. **Spec 文档**：需求或设计变更时立即更新（`.kiro/specs/`）
6. **变更日志**：重要变更必须记录

### 违规后果
- 未同步更新文档的代码变更视为不完整
- 必须立即补充文档后才能继续下一步
- 不允许提交未完成文档的代码

## 版本控制

### Git 规范
- 使用语义化的 commit 信息
- 一个 commit 只做一件事
- 提交前确保代码通过测试
- 不提交敏感信息和临时文件

### 分支策略
- main/master：生产环境代码
- develop：开发环境代码
- feature/*：功能分支
- bugfix/*：bug 修复分支

# 工作流选择指南

本项目有两套工作流系统，适用于不同的开发场景。

## 工作流对比

| 特性 | Kiro Spec 工作流 | 6A 工作流 |
|------|-----------------|-----------|
| **文档位置** | `.kiro/specs/` | `docs/` |
| **适用场景** | 标准功能开发 | 复杂任务、重构 |
| **流程** | Requirements → Design → Tasks → Execute | Align → Architect → Atomize → Approve → Automate → Assess |
| **文档格式** | requirements.md, design.md, tasks.md | ALIGNMENT, CONSENSUS, DESIGN, TASK, ACCEPTANCE, FINAL |
| **测试策略** | 实现优先，测试跟进 | 实现优先，测试跟进 |
| **任务管理** | Kiro 内置任务系统 | 手动管理 |

## 何时使用 Kiro Spec 工作流

**推荐场景**：
- ✅ 开发新功能或特性
- ✅ 需求相对明确
- ✅ 可以拆分为独立的实现任务
- ✅ 需要正式的需求、设计、任务文档
- ✅ 需要使用 Kiro 的任务跟踪功能

**优势**：
- 与 Kiro 深度集成
- 自动任务状态管理
- 支持 Property-Based Testing
- 标准化的文档结构

**示例**：
- 添加新的用户管理功能
- 实现新的 API 端点
- 创建新的 UI 组件
- 优化现有功能

## 何时使用 6A 工作流

**推荐场景**：
- ✅ 进行重大架构重构
- ✅ 需求高度复杂或模糊
- ✅ 涉及多个系统的集成
- ✅ 需要深度的技术调研
- ✅ 快速原型验证
- ✅ 需要更灵活的文档结构

**优势**：
- 更详细的对齐和共识阶段
- 适合处理复杂和模糊的需求
- 灵活的文档结构
- 强调人工审查和决策

**示例**：
- 重构整个认证系统
- 迁移到新的状态管理方案
- 集成第三方支付系统
- 性能优化和架构调整

## 混合使用

在某些情况下，可以混合使用两种工作流：

1. **先用 6A 工作流进行对齐和架构设计**
   - 使用 Align 和 Architect 阶段明确需求和架构
   - 生成 CONSENSUS 和 DESIGN 文档

2. **然后切换到 Kiro Spec 工作流进行实现**
   - 基于 6A 的设计文档创建 Kiro Spec
   - 使用 Kiro 的任务管理进行实现

## 默认选择

**如果不确定使用哪个工作流，默认使用 Kiro Spec 工作流**。

Kiro Spec 工作流更加标准化，与工具集成更好，适合大多数开发场景。只有在遇到特别复杂或特殊的情况时，才考虑使用 6A 工作流。

## 工作流切换

如果在开发过程中发现当前工作流不适合，可以随时切换：

### 从 Kiro Spec 切换到 6A
1. 将 `.kiro/specs/` 中的文档内容迁移到 `docs/`
2. 按照 6A 工作流的格式重新组织文档
3. 继续使用 6A 工作流

### 从 6A 切换到 Kiro Spec
1. 将 `docs/` 中的文档内容迁移到 `.kiro/specs/`
2. 按照 Kiro Spec 的格式重新组织文档
3. 继续使用 Kiro Spec 工作流

## 注意事项

### 文档路径
- **Kiro Spec**：`.kiro/specs/{feature-name}/`
- **6A 工作流**：`docs/{任务名}/`

### 任务管理
- **Kiro Spec**：使用 Kiro 的任务状态管理工具
- **6A 工作流**：手动在文档中标记任务状态

### 测试策略
两种工作流都采用**实现优先，测试跟进**的策略：
1. 先实现核心功能
2. 验证功能正常工作
3. 编写测试确保质量

对于复杂算法或核心业务逻辑，可以选择性地使用 TDD（测试驱动开发）。

## 总结

- **标准功能开发** → 使用 Kiro Spec 工作流
- **复杂任务和重构** → 使用 6A 工作流
- **不确定时** → 默认使用 Kiro Spec 工作流
- **可以混合使用** → 根据项目阶段灵活选择
